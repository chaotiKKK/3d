01 · Das große Bild

→Ein Instrument, das Antworten liefert, nicht nur Dateien

FreeCam3D ist ein Stereo-3D-Scanner, dessen Ausgabe in Game-Asset-Pipelines fließt (Personen/Umgebungen → Photogrammetrie → Blender-Retopo → UE 5.8). Vor dem Overhaul endete der Scan in einem flachen ZIP — die Frage „Ist das brauchbar?" beantwortete erst RealityScan, nach 90 Fotos. Der Overhaul verschiebt das Urteil in das Instrument selbst.

02 · Der Kern des Overhauls

⇄Flacher ZIP → Asset-Bundle

Die alte Form war der falsche Shape: `project.json` + Bilder, ohne Struktur, ohne Qualitätssignal, ohne Winkel-Kontrakt. Neu kommt ein zusätzlicher Dekodier-Durchlauf hinzu, der gleichzeitig Qualität und Kontaktbogen erzeugt.

Vorher — flacher Export
  • freecam3d_project_….zip
  • project.json
  • cam0_….png / cam1_….jpg …
  • …und dann raten:
  • welche Fotos scharf sind
  • welcher Winkel welchem Bild gehört
  • ob die Abdeckung reicht
Urteil? Nirgends. RealityScan zeigt es dir — nach 90 Fotos.
Nachher — Asset-Bundle
  • freecam3d_project_….zip
  • project.json (unverändert, Restore-kompatibel)
  • cam0_….png / cam1_….jpg …
  • scan_meta.json
  • contact_sheet.png
Urteil im Toast: „… — 2 Aufnahme(n) beanstandet" + Badges auf dem Kontaktbogen.
Ein Durchlauf, zwei Ergebnisse

scanShots() dekodiert jeden Blob genau einmal und speist daraus beide Artefakte: die Qualitäts-Flags für scan_meta.json und die Thumbnails für den Kontaktbogen. Bei 150 Fotos = 150 statt 300 Bitmap-Dekodierungen.

03 · Aufnahmepfad

⚙Vier Modi, ein gemeinsamer Schritt

Photo, Burst, Interval und Turntable waren vier Kopien derselben inneren Schleife. Der Overhaul extrahiert sie in captureOne() — die Modi unterscheiden sich nur noch in Namens- und Meta-Konstruktion.

async function captureOne(cam, name, meta, pending){
  const b = await captureBlob(vids[cam]); if(!b) return false;   // Foto/JPEG vom Stream
  tick();                                                       // hörbarer Pieps (Sound-Toggle)
  stampFrame(cam);                                              // Frame → frames[cam]
  addShot(cam, name, tagQuality(cam, meta));                    // Qualität aus dem Frame, meta unverändert
  rememberBlob(name, b, 'image/'+fmt());                        // IndexedDB + blobByName
  pending.push({name: name+'.'+fmt(), blob: b});                // ZIP-Vorbereitung
  return true;
}

● tagQuality — Stempel zur Aufnahmezeit

assessFrame(frames[cam]).flag → meta.quality als Kopie (das Original-Meta wird nie mutiert). Gute Frames tragen keinen Flag → kein Badge; Blur/Dunkel/Hell erscheinen sofort in der Shot-Liste.

● Shot-Liste mit Badges

qBadge(meta) hängt nur Probleme an die Zeile: ⚠ blur ☀ dunkel ☁ hell. Gute Frames bleiben leise — das ✓ erscheint erst im Kontaktbogen.

● Winkel-Typ im Vertrag

Orbit (IMU): meta.imu===true → angle_type:'orbit'. Turntable (getippte Winkel): meta.angle ohne IMU-Flag → 'turntable'. Sonst null.

📄scan_meta.json — maschinenlesbar, additiv, rückwärtskompatibel

Alte Restores ignorieren unbekannte Schlüssel, also bricht der neue Block nichts. Jede Downstream-Stufe findet Winkel, Qualität und Dimensionen ohne Raten.

05 · Die Qualitäts-Triage

▦Wie assessFrame ein Foto beurteilt

Downscale auf 64×48, dann zwei Kennzahlen: Mittelluma (Belichtung) und mittlere Laplace-Varianz (Schärfe/Kontrast). Reine Funktion — keine Seiteneffekte, deterministisch, selftested.

Kalibriert an synthetischen Frames: flach (lv ≈ 0) → blur · Schachbrett (lv ≈ 135) → ok · Schwarz/Weiß → dunkel/hell. Der Schwellwert 14 ist ein Heuristik-Wert — reale Fotos variieren.
✓ ok
⚠ blur
☀ dunkel
kein Bild
Flag-Semantik: null = ok

assessFrame liefert flag: null für scharfe, gut belichtete Frames. Das Literal 'ok' entsteht erst in scanShots per flag || 'ok' — ein selftest-Fehler in diesem Thread entstand genau aus dieser Verwechslung (Check prüfte flag==='ok' gegen den null-Sentinel).

07 · Root Cause unterwegs

🐞Der Export-Bug, den der Rebuild aufdeckte

Der erste End-to-End-Test des Bundles schlug fehl: Bilder wurden nicht eingebettet, alle Qualitäts-Flags waren null. Systematisches Debugging (Phase 1) fand die Ursache am Quellpunkt — nicht am Symptom.

Vorher — Schlüssel statt Record
rememberBlob: blobByName[name] = 42 (IDB-Key)
→ Export: rec.b → undefined → Bild fehlt, Flag null
→ Nach Reload (restoreBlobIndex): Records → Export klappte
→ Live-Sessions exportierten still nie Bilder
Nachher — Record wie überall sonst
rememberBlob: blobByName[name] = {n, b, t} (via dbGet(k))
→ Export: rec.b → Bild eingebettet, Flag korrekt
→ Konsistent mit restoreBlobIndex + Restore-Pfad
Lektion

Zwei Schreibpfade mit unterschiedlichen Shapes in einem Index sind ein Zeitbomben-Muster: blobByName hielt mal Keys (live), mal Records (nach Reload). Der Fix stellt den einen konsistenten Vertrag her — Record {n, b, t} — und die blobByName-Keying-Konvention (Shot-Name ↔ IDB-Record) bleibt erhalten.

09 · Ehrliche Restpunkte

⚖Bewusste Tradeoffs

Was bewusst nicht gebaut wurde

Kein Live-Coach (Coverage-Ring, Bewegungs-Warnungen) — die nötigen Winkel-/Qualitäts-Meta existieren bereits, der Coach ist ein sauberer Folge-Baustein. Kein Amber-Geräte-Fallback in den Rezepten — die maximale Auflösung pro Gerät ist vor der Aufnahme nicht billig bestimmbar; die Auflösungs-Selectliste bietet ohnehin nur unterstützte Größen. Kein HTML-Report — Kontaktbogen + Urteil + JSON tragen die Information; Prosa-Report nur, wenn eine Stufe ihn wirklich braucht.

Bekannte Unsicherheit

Der Blur-Schwellwert (Laplace ≥ 14) ist gegen synthetische Frames kalibriert (flach ≈ 0, Schachbrett ≈ 135) — reale Motive liegen dazwischen, das Heuristik-Risiko (falsch-positive „blur"-Flags bei texturarmen Flächen) ist dokumentiert, nicht wegdiskutiert. Außerdem: Capture-Badges (aus dem gegriffenen Frame) und Export-Flags (aus dem gespeicherten Blob) können theoretisch minimal abweichen — die Export-Flags sind autoritativ.

Erklärt den Asset-Handoff-Overhaul aus diesem Thread (index.html, selftest 69/69, README/AGENTS in Sync).
Alle Werte, Schwellwerte und Kontraktfelder entsprechen dem tatsächlich implementierten Stand — keine dekorativen Zahlen.
